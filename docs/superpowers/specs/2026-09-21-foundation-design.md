# FrontAccounting GraphQL module — Release 1: Foundation — design

Date: 2026-09-21
Status: approved design, pre-implementation. Revised 2026-09-21 after a boot spike
in the container and news from the sgw_sales session; each revision is marked
*(revised)*. Revised again 2026-09-25: the HTTP layer is Slim 4, marked
*(revised: Slim 4)*, and `saygoweb/anorm-graphql` is used from this release on,
marked *(revised: anorm-graphql)*.

## 1. Purpose

`modules/graphql` is a FrontAccounting extension that serves a GraphQL API. It is
built from [Anorm](https://github.com/saygoweb/anorm) models, with Types, Inputs
and tests generated by `saygoweb/anorm-graphql`, and hand-written code where
FrontAccounting demands it.

The first client is the `saygoweb.com-my` hosting panel: a PHP backend calling
server-to-server, which needs to create customers, add recurring invoices and
trigger the sending of them.

The work is split into three releases, each with its own spec and plan:

1. **Foundation** (this document): authentication, FrontAccounting bootstrap, the
   container, the database connection, authorisation, errors, and the docker stack;
   *(revised)* the Slim 4 pipeline, and Type generation proven on one read-only
   entity.
2. **Panel**: reference lookups; customer, branch and contact writes; sales orders
   with a recurring schedule; the `sgw_sales` refactor; the generation list and
   generate-and-send.
3. **Billing**: invoices, customer payments and allocations.

`docs/spec-inputs.md` holds the findings and decisions that led here.

### Decisions this design rests on

- PHP `^7.4 || ^8.0`. `webonyx/graphql-php ^15.32.3`, no `simpod/graphql-utils`.
- Authentication is a JWT granted on user authentication, with a short-lived access
  token and a revocable, rotating refresh token.
- The stack targets the `cambell-prince/frontaccounting` fork at `master-cp`, with
  `sgw_sales` present.
- Discriminated tables (`sales_orders`, `debtor_trans`) are handled by anorm-graphql
  scopes (`ModelType::scope()`, already in `0.1`; a `--config` file later), not composite
  keys. Document-shaped writes are hand-written over FrontAccounting's functions.
  Neither is needed by this release.
- *(revised: Slim 4)* **Slim 4 is the HTTP layer**, with `slim/psr7` and PHP-DI,
  as in the `saygoweb.com-my` panel: a PSR-15 middleware pipeline, real routing for
  later non-GraphQL routes, and one idiom across both ends.
- *(revised: anorm-graphql)* **Types are generated wherever a model can carry one.**
  `saygoweb/anorm-graphql` is a dependency from this release, at `^0.1` (alpha),
  co-developed with this module; `1.0.0` follows once this module is built.
  Section 4.5.
- *(revised)* **`saygoweb/anorm ^3.2.1`, not `^3.2`.** On 3.2.0 `DataMapper::read()`
  and the UPDATE branch of `write()` concatenated the key into SQL; 3.2.1 binds it
  (anorm #76). The floor is what makes `Model::read()` / `readOrThrow()` safe with a
  client-supplied id, so it must not be lowered.

### Goals

1. A request carrying a valid bearer token runs as a real FrontAccounting user, in
   the right company, with that user's role enforced.
2. `login`, `tokenRefresh`, `tokenRevoke` and `me`.
3. Every response is JSON. A FrontAccounting database error is an error, never a
   200 with an HTML body.
4. The pieces Release 2 builds on — container, `\PDO`, `CompanyContext`, `Guard`,
   the error model, the Slim pipeline, `FaModelType` and the generation pipeline —
   exist and are tested. *(revised)*
5. `docker/fa-graphql ci` is green on PHP 7.4 and 8.3.
6. *(revised: anorm-graphql)* One entity, `SalesType`, read-only, travels the whole
   generated path: model, generated Type and tests, `ApiSchema` entry, `Guard`
   areas, and the `http` suite.

### Non-goals

- *(revised: anorm-graphql)* Any business entity other than the read-only
  `SalesType` pilot. Release 2.
- The `sgw_sales` refactor. Release 2.
- Password change, user management, OAuth, per-token scopes.
- An end-to-end test with two companies.

## 2. Request lifecycle *(revised: Slim 4)*

```
index.php                      request from globals (slim/psr7); Config; container; app; run
  app.php                      AppFactory::setContainer(container); middleware; routes
  -- app middleware, outermost first --
  JsonErrorMiddleware          any throwable -> JSON response; the one place exceptions become statuses
  RoutingMiddleware (Slim)     unknown path -> 404, wrong method -> 405 (thrown, rendered above)
  BodyLimitMiddleware          body over max_body_bytes -> 413
  -- route: POST / --
  AuthenticationMiddleware     Authorization: Bearer <jwt> -> Claims in request attribute "claims", or null; bad token -> 401
  FaSessionMiddleware          SessionGate::boot() (Bootstrap); with Claims, enter(): FaSession, CompanyContext::set()
  GraphQLAction                body -> query (400 if not JSON with a "query" string, or a batch);
                               ApiSchema with depth/complexity rules; ErrorFormatter; 200
```

**How errors become responses.** Middleware and the action do not build error
responses; they throw. Slim's `HttpException`s (404, 405), `RequestRejected` (400,
413), `InvalidToken` (401), and `Unauthenticated` / `Forbidden` from the session gate
(401 / 403) are mapped by `JsonErrorMiddleware` to their status in section 6, with
the body `{"errors":[{"message": ..., "extensions":{"code": ...}}]}`. Anything else
is 500 `INTERNAL`, logged in full; with `debug` on, the message and trace are
included. Slim's own `ErrorMiddleware` is not used: it renders HTML unless the
client asks for JSON. Errors raised inside GraphQL execution still go through
`ErrorFormatter` and return 200 with `errors`.

**Failures before the pipeline exists.** If building the app fails — `Config`
failing closed while the container is built, say — `index.php` catches it and emits
a fixed JSON 500 itself. It is the only hand-written response.

**Routing.** `index.php` sets Slim's base path from the directory of
`SCRIPT_NAME`, so the module works wherever FrontAccounting is mounted. The
existing `.htaccess` rewrite already sends non-file paths to `index.php`. This
release registers only `POST /`, as the pattern `/[index.php]` so that a client
posting to `.../index.php` is answered the same way.

**Route-level middleware.** Authentication and the FrontAccounting session are
attached to the GraphQL route, not the app, so a later route (a health check, a cron
trigger) chooses whether it needs a user. The GraphQL route boots FrontAccounting on
every request, anonymous ones included: `login` and `tokenRefresh` need it, and one
code path is simpler than booting lazily for `apiVersion` alone.

**Bootstrap inside the pipeline.** `Bootstrap` installs FrontAccounting's globals and
error handler. Running it inside `FaSessionMiddleware` means a FrontAccounting fatal
error surfaces as `FaErrorException` through `JsonErrorMiddleware`, never as
FrontAccounting's HTML. `Bootstrap` still produces no output and sends no headers;
Slim's emitter sends the only ones.

**Order.** Authentication runs before the body is parsed, so a request with both a
bad token and a bad body gets 401, not 400: the client refreshes first.

### 2.1 `Bootstrap`

`includes/session.inc` cannot be used: it enforces `$page_security`, renders the
login page, starts a cookie session, and wraps output in `ob_start('output_html')`,
which is how FrontAccounting turns a database error into a 200 with an HTML or empty
body.

`Bootstrap::boot()` includes what `modules/api/session-custom.inc` includes, cut to
what an API needs: ~~`errors.inc`~~ *(revised: see below)*, `current_user.inc`, `frontaccounting.php`,
`admin/db/security_db.inc`, the language and gettext includes, `config_db.php`,
`config.php`, `ui/ui_msgs.inc`, `prefs/sysprefs.inc`, `hooks.inc` with every
installed extension's `hooks.php`, `access_levels.inc`, `version.php`, `main.inc`,
`date_functions.inc`, `data_checks.inc`. It sets the globals FrontAccounting
expects (`$path_to_root`, `$SysPrefs`, `$Refs`, `$Ajax`, `$messages`, the default
language in `$_SESSION['language']`). It does **not** install `output_html`, and
sends no headers.

*(revised)* Three things the spike established:

- `Bootstrap` must define `VARLIB_PATH` and `VARLOG_PATH` (`<fa_root>/tmp`) before
  including `config.php`; `session.inc` normally does.
- It includes `includes/session_utils.inc` (`html_specials_encode`,
  `write_login_filelog`, ...). **That file exists only in the
  `cambell-prince/frontaccounting` fork**; upstream keeps those functions inside
  `session.inc`, which cannot be included. Foundation therefore requires the fork
  and fails closed with a message saying so when the file is absent. Supporting
  upstream (by shipping a copy, as `modules/api` does) is out of scope.
  *(revised)* The check runs inside the pipeline, so the `ConfigException` it
  throws reaches `JsonErrorMiddleware`, which answers 500 `INTERNAL` with the
  message `The GraphQL module is not configured: <reason>`, as `index.php` does for
  a configuration failure before the app exists, rather than a bare
  `Internal server error`.
- `TB_PREF` is the literal placeholder `&TB_PREF&`, substituted by `db_query()`.
  The real prefix is `$db_connections[$coy]['tbpref']`, which is what
  `CompanyContext` holds.

*(revised)* **`errors.inc` is not included.** Its `fa_trigger_error()` hands
`E_USER_ERROR` to FrontAccounting's `error_handler()` by a direct function call, not
through `trigger_error()`, so it bypasses `set_error_handler()`; and
`check_db_error()` ends the request with `end_page(); exit` whatever `go_debug` says.
No handler installed by `Bootstrap` can see or stop either. `Bootstrap` loads
`src/Fa/fa_errors_compat.php` in its place, which defines the functions other
FrontAccounting files call by name (`fa_trigger_error`, `display_db_error`,
`frindly_db_error`, `check_db_error`, `get_backtrace`, `exception_handler`,
`fmt_errors`, `error_box`, `end_flush`) and initialises `$messages` and
`$before_box`:

- `fa_trigger_error()` collects every level into `FaMessages`. `display_error()`
  raises `E_USER_ERROR` for validation messages, so the level alone cannot mean
  "stop".
- `display_db_error()` throws `FaErrorException`.
- `check_db_error()` reads the database error, and logs it to `tmp/errors.log`,
  before it rolls back (the rollback resets mysqli's error number), then throws
  `FaErrorException` whenever `$exit_if_error` is set, a friendly duplicate-key
  error included. Nothing after a failed `db_query($sql, $msg)` runs, so nothing
  after a rolled-back `begin_transaction()` can autocommit. Only
  `$exit_if_error = false` with a duplicate key returns.

This is a hand-copied re-implementation and will drift from FrontAccounting's.
**Recommendation: move the seam into the `cambell-prince/frontaccounting` fork
before Release 2's first write**: split `errors.inc` into its logic and its
`error_box`/`fmt_errors` rendering (as the fork already did for
`session_utils.inc`), and have `check_db_error()` / `display_db_error()` throw a
fork-defined exception instead of `end_page(); exit` when a flag such as
`FA_ERRORS_THROW` is defined. The module already requires the fork, so this costs
no compatibility, and FrontAccounting's friendly-error and rollback rules then live
in one maintained place.

*(revised)* **FrontAccounting does not see the HTTP request.** The API reads its
request through PSR-7, built in `index.php` before the app runs. Before any include,
`Bootstrap` empties `$_GET`, `$_POST`, `$_REQUEST`, `$_COOKIE`, `$_FILES` and
`$_SERVER['QUERY_STRING']`: FrontAccounting reads them at include time
(`path_to_root` makes `frontaccounting.php`, `config.php` and `language.inc`
`die()`; `JsHttpRequest=` makes `new Ajax()` install an output handler that rewrites
the body as JavaScript). It forces `display_errors` off, installs its error handler
before the first include, points `error_log` at `$error_logfile` as `session.inc`
does, and discards any output buffer the includes leave open. Release 2 code must
not expect FrontAccounting functions to read request input from the superglobals.

FrontAccounting's root is `../..` from the module directory, overridable in
`config_graphql.php` (`fa_root`).

**No PHP session.** `$_SESSION` is an ordinary array, initialised empty by
`Bootstrap`. There is no `session_start()`, no cookie and no session file. The token
carries identity and FrontAccounting's per-user state is rebuilt from it on every
request. Requests are stateless and safe in parallel.

**Error handler.** `Bootstrap` installs a handler that converts `E_USER_ERROR`
and `E_RECOVERABLE_ERROR` raised through `trigger_error()` into `FaErrorException`.
*(revised)* FrontAccounting's own "DATABASE ERROR" does not reach it: it is thrown
by the `errors.inc` replacement above. FrontAccounting's validation messages,
raised through `display_error()` / `display_warning()` / `display_notification()`,
never reach it either: the replacement's `fa_trigger_error()` collects them into a
`FaMessages` buffer, which `FA_REJECTED` errors draw on (section 6). Deprecations and notices from FrontAccounting's own code are logged,
not thrown: FrontAccounting is not clean under `E_ALL` on PHP 8.

### 2.2 `FaSession`

`FaSession::enter(Claims $claims)`:

1. Refuses a company not present in `$db_connections`.
2. Creates `$_SESSION['wa_current_user'] = new current_user()` and calls
   `set_company($claims->company)`, so `user_company()` answers the token's company.
3. Includes `company/<coy>/installed_extensions.php` and calls `install_hooks()`.
   **Before** the login, as `session.inc` does: `hook_authenticate()` dispatches
   through `$Hooks`, which `install_hooks()` populates from the extensions active
   for that company. It also means other extensions' `db_prewrite` /
   `db_postwrite` hooks fire on writes exactly as in the UI. Then
   `add_access_extensions()` *(revised)*: without it `$security_areas` has no
   `SA_GRAPHQL` and `can_access()` is false for everyone. Only `index.php` and
   `admin/security_roles.php` call it in core.
4. Sets the per-request flag `VerifiedIdentity::set($claims->company,
   $claims->login)`.
5. Calls `$user->login($claims->company, $claims->login, '')`.
6. Clears the flag, whatever the outcome.
7. On `false`, throws `Unauthenticated` — the user was deleted or deactivated since
   the token was issued, or this extension is not active for that company.
8. Requires `can_access('SA_GRAPHQL')`, else `Forbidden`.
9. Creates `$_SESSION['App']` as `session-custom.inc` does.

`current_user::login()` calls `hook_authenticate($login, $password)` before its own
password check. `hooks_graphql::authenticate($login, $password)` returns `true` only
when `VerifiedIdentity` holds exactly that login and the company being logged into,
and `null` otherwise, so FrontAccounting's normal password check runs for every
other caller, including the web UI. FrontAccounting therefore builds the user itself
— role areas, preferences, the inactive check, language — and nothing of
`current_user`'s internals is copied. Because this runs per request, deactivating a
user or changing a role takes effect on the next request.

`VerifiedIdentity` is a final class with private static state, set only by
`FaSession` and cleared in a `finally`. It is the one place where a password check is
bypassed and is tested as such (section 8).

`hook_authenticate()` is `hook_invoke_last`: every active extension's
`authenticate` is called and the **last non-null answer wins**. An extension loaded
after this one that answers `false` for the login would therefore veto a verified
identity; that is the correct reading of an external authentication source saying
no, and it fails closed. The integration suite asserts that a verified identity logs
in with `sgw_sales` active.

`login` (section 3) runs steps 1 to 3, then `current_user::login()` with the real
password and no flag.

### 2.3 Anonymous requests

With no `Authorization` header, `FaSession::enter()` is not called and
`CompanyContext` stays unset. Only `apiVersion`, `login` and `tokenRefresh` resolve;
every other field throws `Unauthenticated`. This is enforced by `Guard`
(section 5), not by schema shape, so introspection shows one schema to everyone.

A header that is present but malformed, badly signed, from the wrong issuer or
expired ends the request with HTTP 401 and a JSON error body before GraphQL
executes: `AuthenticationMiddleware` throws `InvalidToken`. *(revised: Slim 4)*

## 3. Authentication

### 3.1 Schema

```graphql
type Query {
  apiVersion: String!
  me: Viewer!
}

type Mutation {
  login(company: Int = 0, user: String!, password: String!): AuthPayload!
  tokenRefresh(refreshToken: String!): AuthPayload!
  tokenRevoke(refreshToken: String): Boolean!
}

type AuthPayload {
  accessToken: String!
  expiresIn: Int!        # seconds
  refreshToken: String!
}

type Viewer {
  login: String!
  name: String!
  email: String
  company: Int!
  companyName: String!
  areas: [String!]!      # the SA_* codes this user's role holds
}
```

`tokenRevoke` with an argument revokes that token, which must belong to the caller.
Without one it revokes every live refresh token of the caller. It requires a valid
access token either way. It returns `true` when at least one token was revoked.

### 3.2 `login`

1. If the request is not HTTPS and `allow_insecure_login` is false, throw
   `BadInput`: FrontAccounting stores passwords as unsalted MD5, which this module
   cannot change, so a password is not accepted over plain HTTP. HTTPS is
   `HTTPS` on in the request's server params, or `X-Forwarded-Proto: https` when
   `trust_proxy` is true; `RequestInfo::fromRequest()` decides, from the PSR-7
   request. *(revised: Slim 4)*
2. Refuse a company not in `$db_connections`. *(revised)* Refuse, first, a
   company other than one this request has already opened (section 3.6).
3. `current_user::login($company, $user, $password)`. FrontAccounting's own
   failed-login throttle (`login_delay`, `faillog.php`) and any `hook_authenticate`
   extension apply unchanged. *(revised)* FrontAccounting only counts failures and
   greys out its login button; it never refuses on the server. An API is scriptable,
   so `login` refuses with the same `Unauthenticated` message, before checking the
   password, while `check_faillog()` says the caller is throttled. Entering a session
   from a token neither reads nor writes `faillog.php`.

   *(revised)* What that throttle keys on: `check_faillog()` runs before the login,
   when `$_SESSION['wa_current_user']->user` is not yet anyone, and it looks up
   `$login_faillog[<that user>][$_SERVER['REMOTE_ADDR']]` in the one
   `tmp/faillog.php` the whole install shares. So it is a throttle **per remote
   address, across all users and all companies**, and it is shared with the web
   UI's login. Behind a reverse proxy every client has the proxy's address, so
   `login_max_attempts` failures from anyone lock every API and web login out for
   `login_delay` seconds. `trust_proxy` does not change this: it only affects this
   module's `RequestInfo`, never the `REMOTE_ADDR` FrontAccounting keys on. The
   lockout risk is accepted; the README says so for proxied deployments.
4. On failure throw `Unauthenticated` with one message for every cause — unknown
   user, wrong password, inactive.
5. Require `SA_GRAPHQL`, else `Forbidden`.
6. `CompanyContext::set()`, then issue a token pair.

### 3.3 Access token

`lcobucci/jwt ^4.0`, HS256. Claims: `iss` (config `issuer`), `iat`, `nbf`, `exp`
(`access_ttl`, default 900 s), `sub` (FrontAccounting login name), `coy` (company
number, int), `jti` (random). Never stored. Verified on signature, issuer, `nbf` and
`exp` with a 5-second leeway.

### 3.4 Refresh token

32 random bytes, base64url, returned once. Stored only as a SHA-256 hex hash.

`sql/update_1.0.sql`, applied by `activate_extension()` through
`update_databases()` as `sgw_sales` does, so the table exists per company under that
company's prefix:

```sql
CREATE TABLE IF NOT EXISTS `0_graphql_refresh_token` (
  `id` int(11) unsigned NOT NULL AUTO_INCREMENT,
  `user_id` smallint(6) NOT NULL,
  `token_hash` char(64) NOT NULL,
  `issued_at` datetime NOT NULL,
  `expires_at` datetime NOT NULL,
  `revoked_at` datetime DEFAULT NULL,
  `replaced_by` int(11) unsigned DEFAULT NULL,
  `client` varchar(255) NOT NULL DEFAULT '',
  PRIMARY KEY (`id`),
  UNIQUE KEY `token_hash` (`token_hash`),
  KEY `user_id` (`user_id`)
) ENGINE=InnoDB;
```

`user_id` is `0_users.id`. `client` is the User-Agent and remote address, truncated,
for audit only.

The company of a refresh token is not in the token. `tokenRefresh` carries no access
token, so the client sends the refresh token as `<coy>.<secret>`: the company number
selects the connection and prefix, the secret is what is hashed. A wrong company
finds no row.

**`tokenRefresh`:**

1. Parse `<coy>.<secret>`; refuse an unknown company. Open that company's
   connection.
2. Look the hash up. Not found, or expired: `Unauthenticated`.
3. **Reuse detection.** If the row is already revoked, revoke every live token of
   that user and throw `Unauthenticated`. A rotated token presented twice means it
   was copied.
4. Load the user by id; refuse if missing or inactive. *(revised)* This runs
   before anything is written: `RefreshTokenService::rotate()` takes an `$admit`
   callback that it calls with the row's user id after steps 2 and 3 and before
   step 5. `tokenRefresh`'s callback loads `UserModel` and enters the session
   (section 2.2), so a missing, deactivated or no-longer-authorised user is
   refused with the token neither used up nor succeeded.
5. In one transaction: insert the new row, set `revoked_at` and `replaced_by` on the
   old one. *(revised)* The revoke is conditional — `UPDATE ... WHERE id = ? AND
   revoked_at IS NULL` — and `markRevoked()` returns whether it changed a row. When
   it changed none, another request rotated the token first: roll back and treat it
   as reuse (step 3). Checking step 3 alone, outside the transaction, lets two
   concurrent uses of one token both succeed.
6. Return a new pair.

Rows past `expires_at` are deleted opportunistically on `login`, at most 100 per
call. `refresh_ttl` defaults to 30 days.

These writes go through Anorm: FrontAccounting has no functions for this table
(section 4.3).

### 3.5 Configuration

`config_graphql.php` in the module directory: gitignored, denied by the vhost and by
`.htaccess`, documented by a committed `config_graphql.example.php`. It returns an
array:

| key | default | |
|---|---|---|
| `secret` | none | HS256 key. **Required**, at least 32 bytes. |
| `issuer` | `fa-graphql` | `iss` claim. |
| `access_ttl` | `900` | seconds |
| `refresh_ttl` | `2592000` | seconds |
| `allow_insecure_login` | `false` | accept `login` over plain HTTP |
| `trust_proxy` | `false` | honour `X-Forwarded-Proto` / `X-Forwarded-For` |
| `debug` | `false` | include exception detail in `extensions` |
| `max_depth` | `12` | query depth limit |
| `max_complexity` | `2000` | query complexity limit |
| `max_body_bytes` | `1048576` | request body limit |
| `fa_root` | `../..` | FrontAccounting's root |

A missing file, a missing secret or a short secret makes every request fail closed
with HTTP 500 and a JSON error naming the problem. There is no default secret. A file
rather than a `sys_prefs` row, so that a database dump does not contain the key that
mints tokens.

### 3.6 Multi-company *(revised: one company per request)*

The company is fixed at `login` and carried in `coy`. The connection and table
prefix always come from the claim, never from a request argument or header, so a
token for company 0 cannot reach company 1.

**One company per request.** Mutation fields run one after another in one request
and share one container, and the container's `\PDO` is built for whichever company
is open when it is first needed. So a request opens at most one company:

- `FaSession::openCompany()` — which `enter()`, `loginWithPassword()` and
  `tokenRefresh` all go through — refuses any company other than the one already
  open in this request, before looking at it, with `Unauthenticated` ("One company
  per request: send a request for each company."). Re-opening the same company is
  allowed. `Unauthenticated` rather than `BadInput` keeps the single-message rules:
  `tokenRefresh` already turns every `Unauthenticated` from opening its company
  into its one message, "The refresh token is not valid." (section 3.4), and for
  `login` the refusal is decided before any company, user or password is looked
  at, so it says nothing about credentials (section 3.2, step 4).
- The container's `\PDO` is a `CompanyPdo`: it remembers the company it was
  built for, and `prepare()`, `query()`, `exec()` and `beginTransaction()` throw a
  `LogicException` (INTERNAL) when `CompanyContext::company()` is not that company
  or no company is set. It fails closed. `Connection::current()` returns the same
  object, so models built without a PDO are covered too.

Checkpoint D found this reachable without it: a request carrying a company-0 bearer
token and the fields `tokenRevoke` then `tokenRefresh("1.<company-0 secret>")` was
issued a company-1 token when the two companies' databases shared a prefix.
`OneCompanyPerRequestTest` reproduces that shape and the `login` variants.

## 4. Container and database

### 4.1 Container

`container.php` returns a `DI\Container` built with `ContainerBuilder`, one per
request, autowiring on. Explicit definitions *(revised)*: `Config`, `RequestInfo`,
`Clock`, `ErrorFormatter`, `JsonErrorMiddleware`, `BodyLimitMiddleware`,
`Schema` (→ `ApiSchema`), `SessionGate` (→ `FaSession`), `RefreshTokenRepository`
(→ `AnormRefreshTokenRepository`) and `\PDO` (a `CompanyPdo`, section 3.6).
Everything else, `TokenService` included, is autowired. `ApiSchema` takes the container and resolves Types
through a private `type(string $class)` helper that returns
`$this->context->get($class)` — the shape anorm-graphql's scaffolder produces and its
editor expects. Query and Mutation entries are alphabetical. *(revised:
anorm-graphql)* `ApiSchema.php` is scaffolded by `anorm-graphql make`, not written by
hand (section 4.5).

*(revised: Slim 4)* `container.php` returns `function (Config $config, RequestInfo
$request): DI\Container`; `index.php` builds the PSR-7 request first and derives
`RequestInfo` from it. The same container is given to `AppFactory::setContainer()`,
so class-name middleware and the action resolve through PHP-DI.

The container is also the GraphQL context value passed to every resolver.

### 4.2 `CompanyContext`

Static, per request: `company(): int`, `prefix(): string`, `credentials(): array`,
`isSet(): bool`, `set(int $company, array $connection)`, `reset()`.

When unset, `prefix()` answers `0_`, `company()` answers `0`, and nothing queries.
That is what lets `anorm-graphql make` construct models with its `NullPdo`, and unit
tests run, with no request in flight. `credentials()` throws when unset.

### 4.3 Two connections

FrontAccounting runs on its global mysqli connection; Anorm needs PDO. `\PDO` in the
container is a second connection to the same database, built lazily from
`CompanyContext::credentials()`, with `ERRMODE_EXCEPTION`, emulated prepares off and
the charset FrontAccounting uses for that company. It is registered as *the*
connection: anorm-graphql's `ModelType::newModel()` and its generated tests rely on
`$container->get(\PDO::class)`.

The two connections are separate transactions and cannot see each other's
uncommitted rows. The rule, for this and every later release:

> **Within one mutation, write through one side only.**
>
> Document and master-data writes that FrontAccounting has functions for go
> entirely through those functions, inside `begin_transaction()` /
> `commit_transaction()`. Anorm writes only to tables FrontAccounting has no
> functions for. A read that must see a write happens after its commit.

In this release the only writes are refresh tokens, through Anorm.

*(revised)* The one `db_query` in `src` is `src/Fa/fa_errors_compat.php`'s
`db_query('rollback')` on FrontAccounting's own connection, when FrontAccounting
reports a database error (section 2.1). It is what FrontAccounting's own error
path does, it writes nothing, and it touches only the mysqli side, so the rule
above holds: no mutation writes through both sides. `grep -rn
"db_query\|begin_transaction" src` should find only it (and comments).

### 4.4 Models

`src/Model` and `src/Auth/Model` *(revised)*. Conventions, binding on Release 2's
generated and renamed models as well:

- Constructor `__construct(\PDO $pdo = null)`: a null PDO falls back to the
  request's container connection. The first parameter must be the PDO, because
  Anorm's QueryBuilder constructs models as `new $class($pdo)`. No query in a
  constructor.
- The table is `CompanyContext::prefix() . '<table>'`, passed to
  `DataMapper::create()` with an explicit property => column map.
- camelCase domain property names, with declared types; PHP defaults for
  `NOT NULL DEFAULT` columns, because Anorm inserts every property; transformers for
  dates and booleans.

  *(revised)* "Declared types" are `@var` docblock types, as `anorm make` drafts
  them and `SalesTypeModel` has them, not PHP typed properties. Booleans: all three
  models conform (`UserModel::$inactive` is a `bool` through `BooleanTransform`).
  Dates: `RefreshTokenModel`'s three datetimes stay `Y-m-d H:i:s` strings, because
  its columns hold UTC and Anorm's `SqlDateTimeTransform` reads and writes in PHP's
  default timezone, which FrontAccounting sets from its own configuration. Its one
  reader, `AnormRefreshTokenRepository`, converts them to and from
  `RefreshTokenRecord`'s `DateTimeImmutable`s with an explicit UTC zone. A model
  that becomes API surface uses a transformer for its dates.
- `$mapper->modelPrimaryKey` set where the key is not `id`.
- Static mode only. No `MODE_DYNAMIC`.

This release ships `RefreshTokenModel` and `UserModel` (`0_users`, read-only, never
exposing `password`) and the pilot `SalesTypeModel`.

*(revised: anorm-graphql)* `src/Model`, namespace `FA\GraphQL\Model`, holds only
models meant to become API surface, because it is the folder the generator scans
(section 4.5). Models that must never be exposed live in `src/Auth/Model`, namespace
`FA\GraphQL\Auth\Model`: `RefreshTokenModel` and `UserModel`. A mistake in the
generator's options can then only leave an entity out, never expose a refresh token.

### 4.5 Generated Types: `anorm-graphql` *(revised: anorm-graphql)*

Types are generated from Anorm models wherever a model can carry one: database →
`anorm make` → models in `src/Model` → `anorm-graphql make` → Types, Inputs, tests
and `ApiSchema.php` entries. Types are hand-written only where FrontAccounting
demands it: document-shaped writes over FrontAccounting's functions, joins (the
`sgw_sales` generation list), composite keys a scope cannot express, and what is not
a table (the auth payloads, `me`).

**Dependency.** `saygoweb/anorm-graphql ^0.1`, a runtime `require`: the generated
code extends its `ModelType` and uses `GraphQLUtils` and `MangoInput` at request
time. It is not on Packagist; `composer.json` names its GitHub repository as a `vcs`
repository. `v0.1.0` is its first alpha, and the two repositories are co-developed
through the alpha: a change this module needs goes into `anorm-graphql` as a `0.x`
release, not a workaround here. `1.0.0` follows once this module is built. For local
co-development, `bin/generate` runs the generator from a host checkout named by
`ANORM_GRAPHQL_CHECKOUT` (for example `../../../anorm-graphql`), with this module's
`vendor/autoload.php` prepended so the models load. For the runtime in the container,
`ANORM_GRAPHQL_PATH` mounts the checkout at `/opt/anorm-graphql` for a local-only
composer `path` repository (never committed; `composer.lock` must point at the tag).
That symlink resolves only inside the container, which is why host generation uses
`ANORM_GRAPHQL_CHECKOUT` rather than `vendor/`.

**Prerequisite in `anorm-graphql` `v0.1.0`: `--type-base <class>`.** The generated
`<Entity>TypeBase` extends the named class instead of `Anorm\GraphQL\ModelType`; the
named class must itself extend `ModelType`. This is a change in the `anorm-graphql`
repository, with its own tests, made and tagged before this module depends on it.

**`FA\GraphQL\Type\FaModelType`** — abstract, extends `ModelType`:

- `abstract protected function areas(): array` — verb => `SA_*` area.
- `authorize($verb, $model, $context)` calls `Guard::requireFor($this->areas(),
  $verb)`.
- `newModel()` is inherited: `ModelType` already constructs the model on the
  container's `\PDO`.

Every generated Type fails closed twice: a Type without `areas()` cannot be
instantiated, and a verb missing from `areas()` is `Forbidden`.

**`bin/generate`**, a shell script, runs `php vendor/bin/anorm-graphql.php make` with
the module's fixed options (`composer generate` calls the same script):

```
-m src/Model -n 'FA\GraphQL\Model' -o src/Type -t 'FA\GraphQL\Type'
--tests tests/Generated --test-ns 'FA\GraphQL\Tests\Generated'
-s src/ApiSchema.php --schema-ns 'FA\GraphQL'
--type-base 'FA\GraphQL\Type\FaModelType' --readonly SalesType
```

It runs on the host with the host's `php` (no Composer needed there): the generator
constructs models on a `NullPdo` and needs no database and no container. It must run from this module's `vendor/bin`, because it
`require`s the model files and they use this module's classes (`CompanyContext`).
Extra arguments pass through: `bin/generate --dry-run`. The read-only list lives in
the script.

**`ApiSchema.php`** is scaffolded by the first `make`. `apiVersion`, `me` and the auth
mutations are then added by hand, without the `// anorm-graphql` marker, so the
generator never touches them.

**Generated tests.** `tests/Generated/TestCase.php` is scaffolded once and is ours:
`createContainer()` boots FrontAccounting and enters a session as `apitest` through
`FaSession`, so generated tests pass through the real `Guard`; `createSchema()`
returns `ApiSchema`. They belong to the `integration` suite and run in separate
processes. They roll back on the container's `\PDO`; FrontAccounting's tables are
InnoDB.

**The pilot: `SalesType`**, read-only. `SalesTypeModel` is made by `anorm make` from
`0_sales_types` and renamed to the conventions of section 4.4. The generator
produces `SalesTypeTypeBase`, `SalesTypeType`, the `salesTypeList(query:
MangoInput)` entry and `SalesTypeTypeTest`. `SalesTypeType::areas()` is `['list' =>
'SA_SALESTYPES']`. The seed role gains `SA_SALESTYPES`.

## 5. Authorisation

`SA_GRAPHQL` is the outer gate: checked at `login` and in `FaSession::enter()`.

*(revised)* No role holds it until someone grants it — not even System
Administrator. FrontAccounting renumbers extension areas by extension id:
section `(id << 16) | (100 << 8)`, first area `section | 100`. With this module
registered as extension 1, as the docker entrypoint does, that is section `91136`
and area `91236`, and those are the literals `tests/data/seed.sql` appends to the
test role's `sections` and `areas`.

`Guard` is the inner one:

- `Guard::authenticated()` throws `Unauthenticated` unless a user is logged in.
- `Guard::require(string $area)` calls `authenticated()`, then throws `Forbidden`
  unless `$_SESSION['wa_current_user']->can_access($area)`.
- `Guard::requireFor(array $areas, string $verb)` looks the verb up and **throws
  `Forbidden` when the verb has no entry**. A forgotten mapping fails closed.

FrontAccounting's existing `SA_*` areas are used; no per-entity areas are added. A
panel user gets a role holding `SA_GRAPHQL` plus the sales areas it needs.

Every resolver in this release calls `Guard` first, except `apiVersion`, `login` and
`tokenRefresh`.

*(revised: anorm-graphql)* Generated Types reach `Guard` through `FaModelType`
(section 4.5): each declares `areas()`, for example `['list' =>
'SA_SALESTRANSVIEW', 'create' => 'SA_SALESORDER']`, and `authorize()` calls
`Guard::requireFor($this->areas(), $verb)`. Foundation ships it, proven by the
`SalesType` pilot.

## 6. Errors and limits

Every response body is JSON.

*(revised: Slim 4)* Every non-200 status is thrown and rendered by
`JsonErrorMiddleware`, except the 500 `index.php` writes when the app cannot be built.

| HTTP | when | thrown by |
|---|---|---|
| 200 | every executed GraphQL request, including ones with `errors` | — (`GraphQLAction`) |
| 400 | unparseable body, no `query` string, or a batch | `GraphQLAction` (`RequestRejected`) |
| 401 | `Authorization` header present but malformed, badly signed, wrong issuer, or expired | `AuthenticationMiddleware` (`InvalidToken`) |
| 401 | *(revised)* the session gate refuses the identity (user deleted, deactivated, or the extension inactive for that company) | `FaSessionMiddleware` (`Unauthenticated`) |
| 403 | *(revised)* the session gate forbids it (the role lacks `SA_GRAPHQL`) | `FaSessionMiddleware` (`Forbidden`) |
| 404 | *(revised)* no route for the path | Slim routing (`HttpNotFoundException`) |
| 405 | not POST; the response carries `Allow: POST` | Slim routing (`HttpMethodNotAllowedException`) |
| 413 | body over `max_body_bytes`, by `Content-Length` or by its real size | `BodyLimitMiddleware` (`RequestRejected`) |
| 500 | configuration fails closed; any unrecognised throwable (`INTERNAL`) | `index.php`; `JsonErrorMiddleware` |

401 is outside GraphQL so a client can refresh and retry without parsing the body.
Each `ApiError` declares the HTTP status it has when thrown outside GraphQL
(`Unauthenticated` 401, `Forbidden` 403); inside GraphQL it is an entry in `errors`
of a 200.

*(revised: Slim 4)* Errors that end the request before GraphQL, other than
`ApiError`s, carry a code by status: 400 `BAD_REQUEST`, 404 `NOT_FOUND`, 405
`METHOD_NOT_ALLOWED`, 413 `PAYLOAD_TOO_LARGE`; an `InvalidToken` is 401
`UNAUTHENTICATED`.

Client-safe errors implement webonyx's `ClientAware` and carry `extensions.code`:

| code | class | |
|---|---|---|
| `UNAUTHENTICATED` | `Unauthenticated` | no valid identity; bad credentials; bad refresh token |
| `FORBIDDEN` | `Forbidden` | identity lacks the security area |
| `BAD_INPUT` | `BadInput` | input failed this module's validation |
| `NOT_FOUND` | `NotFound` | a referenced row does not exist |
| `FA_REJECTED` | `FaRejected` | FrontAccounting refused; carries its own messages from the `FaMessages` buffer in `extensions.messages` |

Anything else reaches the client as `Internal server error` with
`extensions.code = INTERNAL`, and is logged in full to FrontAccounting's
`tmp/errors.log`. With `debug` on, the message and trace are included under
`extensions`.

`FaRejected` is defined here and first thrown in Release 2.

**Limits.** webonyx's `QueryDepth` and `QueryComplexity` rules from `max_depth` and
`max_complexity`; `max_body_bytes` on the raw body before parsing. Introspection
stays on: the API serves authenticated server clients, and the panel's code
generation uses it. Batched queries (a JSON array body) are refused with 400.
